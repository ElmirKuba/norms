# Инвайты и доступ

Система закрытая — регистрация только по коду приглашения. Исключение: dev-режим с флагом свободной регистрации.

## Feature flags

Флаги приходят с бэка по API (не захардкожены в бандл). Эндпоинт: `GET /api/v1/app/feature-flags` — публичный (без авторизации). Подробнее: [`api-contracts.md`](api-contracts.md).

В JSON используется snake_case, в Angular коде — camelCase через маппер.

| Флаг (JSON) | Назначение |
|---|---|
| `dev_mode` | Показывать dev-элементы UI |
| `free_registration` | Регистрация без инвайт-кода (для разработки / раннего этапа) |

## UI flow (нативная прила)

### Главный экран (неавторизован)
Две кнопки: **Авторизация** и **Регистрация**.

### Авторизация
- Поле ввода: логин (UIN или username — бэк сам определяет что получил).
- Поле ввода: пароль.
- Кнопка: **Войти**.

### Регистрация
Если `freeRegistration` выключен:
1. Сначала экран ввода инвайт-кода (10 цифр) + кнопка **Принять приглашение**.
2. Бэк проверяет код: существует, не истёк → допускает к регистрации.

Далее (или сразу если `freeRegistration` включен):
- Поле ввода: пароль.
- Кнопка: **Создать аккаунт**.

UIN генерируется асинхронно после создания аккаунта (см. [`identity.md`](identity.md)).

## Инвайт-код

- **Формат:** 10 цифр, генерируется случайно.
- **Одноразовый** — после использования запись удаляется из таблицы.
- **Коллизии:** unique-индекс + retry при генерации.
- **TTL при создании:** фиксированный, задаётся через env `INVITE_TTL_DAYS` (default 7 дней). Фронт не передаёт дату — сервер вычисляет `expires_at = now + INVITE_TTL_DAYS`.

## Таблицы

> Полное DDL — в [`database-schema.md`](database-schema.md).

### invites (коды приглашений)

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `text` PK | Универсальный ID (см. [`database.md`](database.md)) |
| `account_id` | `text` FK | Кто создал (→ `accounts.id`). `ON DELETE CASCADE` — активные коды инвалидируются при удалении создателя |
| `code` | `text` unique | 10-значный код |
| `expires_at` | `timestamptz` | До какого момента код валиден (включительно) |
| `created_at` | `timestamptz` | |

### referrals (кто кого пригласил)

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `text` PK | Универсальный ID |
| `inviter_id` | `text` FK nullable | Кто пригласил (→ `accounts.id`). `ON DELETE SET NULL` — приглашённый остаётся, инвайтер показывается как «удалённый аккаунт» |
| `invitee_id` | `text` FK unique | Кого пригласили (→ `accounts.id`). `ON DELETE CASCADE` — приглашённый удалил аккаунт = запись бесполезна |
| `created_at` | `timestamptz` | Когда приглашение принято |

### accounts — столбец

| Поле | Тип | Заметки |
|---|---|---|
| `invites_remaining` | `integer`, default 3 | Сколько инвайтов осталось. Декремент при создании кода, инкремент при отзыве. Админ может пополнить через БД / админку |

## Эндпоинты

См. [`api-contracts.md`](api-contracts.md#http--invites).

| Эндпоинт | Назначение |
|---|---|
| `POST /api/v1/invite/check` | Проверка кода до регистрации, без потребления. Public, rate-limit по IP |
| `POST /api/v1/invite/create` | Создание кода, атомарный декремент `invites_remaining` |
| `GET /api/v1/invite/read-list` | Свои активные коды |
| `DELETE /api/v1/invite/revoke/:id` | Отзыв кода, инкремент `invites_remaining` |
| `GET /api/v1/invite/read-referrals` | Кто пригласил меня + кого пригласил я |

## Логика

### Создание инвайта
Один запрос, одна транзакция: проверить `invites_remaining > 0`, сгенерировать 10-значный код с retry на коллизии (unique-индекс), записать в `invites` с `expires_at = now() + INVITE_TTL_DAYS`, декрементировать `invites_remaining` в `accounts`.

### Использование инвайта (внутри `POST /account/create`)

Атомарно в одной транзакции (см. [`database-schema.md`](database-schema.md#создание-аккаунта)):

1. Найти `invites` по `code`. Нет → `404 invite_not_found`.
2. `expiresAt < new Date()` → удаляем запись, `410 invite_expired`. `invites_remaining` инвайтеру **не возвращается** — TTL истёк по его решению.
3. Иначе — удаляем `invites`-запись, создаём `accounts`, создаём `referrals` (`inviterId = invite.accountId`, `inviteeId = newAccountId`), создаём первую `sessions`.

### Отзыв инвайта

`DELETE /api/v1/invite/revoke/:id` в одной транзакции: удалить запись из `invites` (проверка владельца через `WHERE id=? AND account_id=?`, иначе `404 invite_not_found` / `403 not_your_invite`), инкрементировать `invites_remaining`.

### Просроченные коды

GC нет. Записи удаляются при попытке использования через `account/create`. `invite/check` НЕ удаляет просроченные — для проверяющего не отличает «не найден» и «истёк» (одна ошибка `404 invite_not_found`), чтобы не позволять перебирать пространство активных кодов.

### Rate-limit на `invite/check`

`check-invite.use-case.ts`:

| Параметр | Значение | Где |
|---|---|---|
| Ключ | `invite:check:ip:{ip}` | Redis |
| Лимит | 10 попыток | `_maxAttempts` const |
| Окно | 900 сек (15 минут) | `_windowSec` const |
| Ответ при превышении | `429 rate_limited` | `RATE_LIMITED` error code |

## UI в настройках

- Кнопка **Пригласить** — создать новый код (если `invites_remaining > 0`).
- Таблица **Мои приглашения** — активные коды, можно отозвать.
- Таблица **Приглашённые мной** — список людей (из `referrals`), дата.
- **Кто меня пригласил** — видно из `referrals` по `invitee_id`.
