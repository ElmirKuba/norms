# Чаты и E2E шифрование

## Модель чата

Чат = соединение между двумя конкретными **устройствами** (сессиями) двух аккаунтов. Технически device-to-device, но в UI первично показывается аккаунт (имя, UIN). Устройство видно через доп. инфо (три точки → тултип).

- Между одной парой устройств — безлимитное количество чатов.
- Уникальность: название чата (case-insensitive) уникально в пределах пары устройств.
- Название чата одинаковое для обеих сторон. При переименовании — оба узнают.
- Название чата **не шифруется** (метаданные на сервере).

## Создание чата — flow

1. Захожу в профиль аккаунта → кнопка "написать".
2. Модалка: список устройств аккаунта (из `sessions`). Приоритет отображения: мой локальный псевдоним > nickname устройства > system_name. Через три точки — вся инфо (nickname + system_name).
3. Выбираю устройство, ввожу название чата.
4. Моё устройство генерирует пару ключей ECDH (P-256 или X25519, Web Crypto API).
5. Публичный ключ уходит на сервер, чат в статусе **pending_key**.
6. Когда устройство собеседника онлайн — оно получает запрос, генерирует свою пару, отправляет свой публичный ключ.
7. Обе стороны вычисляют общий секрет (ECDH) → выводят симметричный ключ AES-256-GCM.
8. Сервер удаляет публичные ключи после обмена. Чат → статус **active**.

**Оптимистичная отправка:** сразу после создания чата можно писать. Сообщения хранятся локально в статусе `pending_key`, шифруются и отправляются автоматически когда обмен ключами завершён.

## Шифрование

Гибридная схема (стандарт для всех E2E мессенджеров):

1. **ECDH** (P-256 / X25519) — каждая сторона чата генерирует пару ключей. Из двух публичных ключей математически выводится общий секрет. Секрет никогда не передаётся по сети.
2. **AES-256-GCM** — из общего секрета выводится симметричный ключ. Все сообщения шифруются им. Быстро, любой размер, невзламываемо (2^256 комбинаций).

Два уровня защиты: TLS (транспорт WSS) + E2E (содержимое AES-256-GCM).

### Почему не чистая асимметрика
RSA-4096 шифрует максимум ~446 байт. ECC (ECDH) вообще не шифрует данные — только вычисляет общий секрет. Поэтому гибридная схема: асимметрика для обмена секретом, симметрика для данных.

## Ключи

- Каждый чат — своя пара ключей ECDH у каждой стороны.
- Приватный ключ **никогда** не покидает устройство. Хранится в локальной SQLite, зашифрован мастер-ключом устройства.
- Публичные ключи передаются через сервер только при создании чата, после обмена — сервер удаляет.
- Forward secrecy (Double Ratchet) — **не в MVP**. Статичные ключи на чат.

## Доставка сообщений

```
А пишет Б:
1. Шифрует сообщение AES-256-GCM (общий ключ чата)
2. Отправляет по WSS (TLS)
3. Сервер хранит зашифрованный blob до доставки
4. Б выходит онлайн → сервер доставляет → Б расшифровывает
5. После подтверждения доставки сервер удаляет blob
```

### Недоставленные сообщения
Сервер хранит зашифрованные blob'ы пока устройство не выйдет онлайн — без лимита по времени. Если устройство кикнуто (сессия удалена) — сообщения сохраняются, доставятся когда авторизуется заново (MVP-решение).
