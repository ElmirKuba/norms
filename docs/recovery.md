# Recovery (восстановление доступа)

Восстановление пароля через секретные вопросы и ответы. Принципиально не зависит от провайдеров (email/sms/телефон не привязываются к аккаунту).

## Что восстанавливает recovery

| Сценарий | Аккаунт восстанавливается? | Чаты восстанавливаются? |
|---|---|---|
| **Пароль забыт, то же устройство, прила НЕ переустанавливалась** | ✅ | ✅ (мастер-ключ в keychain, SQLite на месте) |
| **Пароль забыт, прила переустановлена / данные очищены** | ✅ | ❌ (SQLite удалён вместе с прилой; даже если keychain выжил, расшифровывать нечего) |
| **Устройство потеряно / новое устройство** | ✅ | ❌ (приватные ключи чатов остались на старом устройстве) |
| **Q/A не настраивались** | ❌ | ❌ |

**Recovery возвращает аккаунт, не чаты.** Это фундаментальное свойство E2E. UI обязан явно объяснить это при настройке Q/A.

## Сценарий «то же устройство — keychain выжил, SQLite нет»

iOS/macOS Keychain по умолчанию переживает удаление прилы. Но локальная SQLite (в `Filesystem.Directory.Data` / `app.getPath('userData')`) удаляется. Без расшифрованной истории и зашифрованных приватных ключей мастер-ключ бесполезен.

**Принцип**: при первом запуске прилы проверяем — если SQLite пуст, а в keychain есть мастер-ключ, удаляем сиротский ключ. Это устройство считается новым.

## Хеширование

- **Пароль** хешится на сервере, **argon2id**. Plain-text идёт по TLS — допустимо, реальный секрет (приватные ключи чатов) на сервер не попадает никогда.
- **Ответ на секретный вопрос** хешится так же — argon2id, индивидуальная соль на каждую запись.
- **Нормализация ответа перед хешем:** `trim → toLowerCase → collapse multiple spaces → unicode NFC`. Иначе «Москва» и «москва » будут разными ответами.
- Сам **вопрос** хранится открытым текстом (юзер должен его прочитать).

## Q/A — модель

- **Источник вопросов:** микс. Сервер отдаёт готовый список (~10 базовых: «Девичья фамилия матери», «Кличка первого питомца», «Город рождения отца», и т.д.), юзер может выбрать любые из них И/ИЛИ добавить свои с произвольным текстом вопроса.
- **Количество:** не ограничено. Юзер сам решает, сколько задать.
- **Логика восстановления:** OR — достаточно ответить корректно на ОДИН любой из заданных вопросов.
- **Когда настраивается:** в настройках аккаунта после авторизации. Без принуждения, без баннеров. Не настроил — не восстановишь.

## Таблицы

### `recovery_questions` (на сервере)

| Поле | Тип | Заметки |
|---|---|---|
| `id` | string PK | Универсальный ID (см. [`database.md`](database.md)) |
| `account_id` | string FK | → `accounts.id`. One-to-many: один аккаунт — много Q/A |
| `question` | string | Текст вопроса (открыто). Может быть из preset-списка или своя формулировка |
| `answer_hash` | string | argon2id хеш нормализованного ответа |
| `answer_salt` | string | Индивидуальная соль |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

### `accounts` — без новых столбцов
Связь только через `recovery_questions.account_id`.

## Flow

### Настройка Q/A (в настройках)
1. Юзер открывает раздел «Восстановление доступа».
2. Клиент запрашивает `GET /api/v1/recovery/preset-questions` (см. [`api-contracts.md`](api-contracts.md)) — бэк отдаёт список preset-вопросов. Рядом — поле «Свой вопрос».
3. Для каждого выбранного вопроса — вводит ответ.
4. Клиент шлёт `[{ question, answer }]` на бэк по HTTPS.
5. Бэк нормализует ответы, хеширует argon2id, пишет в `recovery_questions`.

### Удаление / редактирование Q/A
- Удалить отдельную пару — DELETE по `id`.
- Изменить ответ — обновляет `answer_hash` + `answer_salt` + `updated_at`.
- Изменить вопрос — то же.

### Восстановление пароля
1. На экране авторизации — кнопка «Забыли пароль?».
2. Юзер вводит UIN или username.
3. Бэк проверяет: существует аккаунт? Есть ли у него Q/A?
   - Нет аккаунта → ошибка «не найден».
   - Аккаунт есть, Q/A нет → ошибка «recovery не настроен, восстановление невозможно».
4. Бэк отдаёт **список вопросов** (только `question`, без хешей).
5. Юзер выбирает один вопрос, вводит ответ.
6. Клиент шлёт `{ account_id, question_id, answer }` на бэк.
7. Бэк нормализует ответ, проверяет argon2id-хеш по соли из этой записи.
   - Не совпало → инкрементируем счётчик неудачных попыток (см. ниже), возвращаем ошибку.
   - Совпало → возвращаем одноразовый `reset_token` (TTL 10 минут).
8. Юзер вводит новый пароль + `reset_token`.
9. Бэк проверяет токен, обновляет `password_hash` в `accounts`.
10. **Сессии остаются нетронутыми.** Всем онлайн-сессиям прилетает WSS-уведомление: `password_reset_via_recovery` (UI показывает баннер «Пароль был сброшен через секретные вопросы. Если это не вы — кикните подозрительные устройства»).

## Защита от brute-force

Q/A — слабее пароля (ответы часто короткие, словарные). Без rate-limit взламывается перебором.

- **Per-account counter** неудачных попыток ответа за окно времени.
- 5 неудач за 10 минут → блок попыток на 1 час.
- 5 неудач после разблокировки → блок на 24 часа.
- 5 неудач ещё раз → блок на 7 дней.
- Счётчик сбрасывается при **успешном логине** (не при успешном recovery — иначе можно сбросить через recovery и продолжить).

Реализация — таблица `recovery_attempts` или Redis-счётчик (если `SESSION_STORE=redis` уже подключён, переиспользуем).

## UI

### При настройке Q/A — обязательное предупреждение
Модалка / inline-блок на странице:

> **Recovery вернёт доступ к аккаунту, но не вернёт чаты.**
>
> Если устройство потеряно или прила была переустановлена — приватные ключи чатов восстановить нельзя. Это особенность сквозного шифрования.
>
> Recovery полезен в одном сценарии: ты забыл пароль, но устройство при тебе и прилу не переустанавливал.

Без принятия этого блока — кнопка «Сохранить вопросы» неактивна.

### В разделе «Восстановление доступа»
- Список заданных Q/A (вопрос + дата установки + кнопки редактирования/удаления).
- Кнопка «Добавить вопрос» → preset-список + опция «Свой».
- Никаких напоминаний/баннеров о настройке recovery в других разделах прилы. Если юзер сюда не зашёл — он сам решил.
