# Идентификация пользователей

> Полное DDL обеих таблиц — в [`database-schema.md`](database-schema.md).

## Сущности

### Account
Учётная запись. Создаётся при регистрации.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `text` PK | Универсальный ID (см. [`database.md`](database.md)) |
| `password_hash` | `text` | argon2id (хешируется на сервере, см. ниже Login) |
| `username` | `citext` nullable, unique | CITEXT даёт регистронезависимую уникальность нативно. Выдаётся только админом. Формат — см. ниже |
| `nickname` | `text` nullable | Произвольный display name (кириллица, пробелы, что угодно). Не используется для логина и поиска. Меняется через `PATCH /api/v1/account/update`. Приоритет отображения в UI: `nickname > @username > UIN` |
| `invites_remaining` | `integer`, default 3 | Сколько инвайтов осталось (см. [`invites.md`](invites.md)) |
| `is_admin` | `boolean`, default false | Флаг админа. Назначается напрямую через БД. Admin-эндпоинты пока не реализованы |
| `created_at`, `updated_at` | `timestamptz` | |

### UIN
Числовой публичный идентификатор. 1:1 с Account. Хранится отдельной таблицей — изолируем логику генерации, резервирования "красивых" номеров и потенциального обмена/продажи.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `text` PK | Универсальный ID |
| `account_id` | `text` FK nullable | Partial unique (`WHERE account_id IS NOT NULL`). NULL — зарезервированный UIN, ещё не выдан или возвращён в пул |
| `number` | `text` unique | Сама последовательность цифр |
| `is_premium` | `boolean`, default false | «Красивый» UIN. При удалении аккаунта — отвязывается (account_id = NULL), а не удаляется |
| `created_at`, `updated_at` | `timestamptz` | |

**FK-стратегия:** `ON DELETE NO ACTION` — удаление аккаунта обрабатывается в коде в транзакции (см. [`database-schema.md`](database-schema.md#удаление-аккаунта)). Премиум возвращается в пул, обычный удаляется.

## UIN — генерация

- **Формат:** только цифры. Длина начинается с **4** (1000–9999).
- **Авторасширение:** когда пул длины N исчерпан — генератор переключается на N+1. Максимум 10 цифр.
- **Случайность:** UIN выдаются псевдослучайно, **не последовательно**. Сначала может прийти `4937`, потом `9378` — чтобы не давать оценку числа аккаунтов и не создавать "престиж" по счётчику.
- **Асинхронность:** регистрация **не блокируется** генерацией. Account создаётся, ставится task в очередь генерации UIN, фронт получает UIN позже (поллинг или push).
- **Коллизии:** unique-индекс на `uins.number` + retry в задаче. Очередь — BullMQ на Redis (см. [`backend-stack.md`](backend-stack.md)).

## "Красивые" UIN

`1111`, `2222`, `12345`, `11111`, повторы, лесенки и т.п. — резервируются заранее скриптом со `account_id = NULL`. На будущее — монетизация (продажа/обмен). Конкретный список паттернов и правила резервирования — отдельный TODO.

## Username

- **Длина:** 3–30 символов включительно.
- **Алфавит:** `a-z`, `A-Z`, `0-9`.
- **Первый символ — не цифра** (буква). Регекс: `^[a-zA-Z][a-zA-Z0-9]{2,29}$`. Иначе `12345` парсилось бы и как UIN, и как username — поиск/login не отличили бы их.
- **Регистронезависимый** — `Petya` и `petya` считаются одним именем (для поиска и уникальности через `CITEXT`).
- **Кому выдаётся:** только своим — вручную админом через БД или через админ-панель в приложении. Юзер сам username не выбирает.

Username — **не login**. Это "ник для своих", фича доверенных аккаунтов.

## Пароль

**Валидация:**
- Минимум **8 символов**.
- Без верхнего ограничения (argon2id не зависит от длины входа).
- Без требований к составу (цифры, спецсимволы и т.п.) — юзер сам решает. Сложность ≠ безопасность при наличии rate-limit и argon2id.
- Валидация длины — и на фронте (UX), и на бэке (безопасность).

**Хеширование:** argon2id на сервере. Plain-text идёт по TLS — допустимо, реальный секрет (приватные ключи чатов) на сервер не попадает.

## Login

**Login = UIN или username.** Бэк определяет тип регексом `/^\d+$/`:
- Строка из одних цифр → UIN, exact match по `uins.number`.
- Иначе → username, exact match по `accounts.username` (CITEXT, регистронезависимо).

Регекс username (`^[a-zA-Z][a-zA-Z0-9]{2,29}$`) гарантирует, что username не может состоять из одних цифр → множества не пересекаются.

Реализация: `_findAccount()` в `auth-account.use-case.ts`.

- Клиент поддерживает **мульти-аккаунт**: несколько Account залогинено одновременно, переключение в UI.
- Восстановление пароля — через секретные вопросы. Подробнее: [`recovery.md`](recovery.md).
- **Rate-limit на неудачные login-попытки** — см. [`auth-devices.md`](auth-devices.md#rate-limit).

## Регистрация — flow

1. Юзер вводит пароль и (если `feature-flags.free_registration === false`) инвайт-код. Запрос: `POST /api/v1/account/create` с `{ password, invite_code, system_name, platform }`.
2. Бэк в транзакции: проверяет/потребляет инвайт, создаёт Account (без UIN), создаёт первую сессию, пишет `referrals`.
3. Бэк ставит BullMQ-job `uin-generation` (после коммита) и возвращает токены — фронт **сразу авторизуется**, не ждёт UIN.
4. На UI висит модалка `UinModalService.openUinPending()`: «Не выходите из аккаунта, пока не получите UIN — UIN это ваш логин, без него восстановить аккаунт нельзя.»
5. Когда UIN сгенерирован — приходит WSS-событие `uin_assigned`, модалка снимается, UIN отображается в профиле. Альтернатива (если WSS не подключён): поллинг `GET /api/v1/uin/read-status`.

Решение принято как концептуальный workaround. Минусы (юзер всё-таки может выйти до выдачи UIN) осознаются.

## Поиск и взаимодействие

- **Поиск:** `GET /api/v1/search?q=...&limit=20`. Логика разбора `q` — та же, что и для логина:
  - Цифры → exact match по `uins.number`.
  - Буквы → CITEXT-поиск по `accounts.username` (через `pg_trgm` или ILIKE — детали в `search.use-case.ts`).
- **Открытие профиля:** через `GET /api/v1/account/read?id=...` или `?uin=...`.
- **Приватность:** настройки «кто может писать» — не реализованы (MVP: всё открыто). См. [`privacy.md`](privacy.md).
