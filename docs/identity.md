# Идентификация пользователей

## Сущности

### Account
Учётная запись. Создаётся при регистрации.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | string PK | Универсальный ID (см. [`database.md`](database.md)) |
| `password_hash` | string | argon2id (хешируется на сервере, см. ниже Login) |
| `username` | string nullable, unique (case-insensitive) | См. ниже — выдаётся только админом |
| `invites_remaining` | integer, default 3 | Сколько инвайтов осталось (см. [`invites.md`](invites.md)) |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

### UIN
Числовой публичный идентификатор. 1:1 с Account. Хранится отдельной таблицей — изолируем логику генерации, резервирования "красивых" номеров и потенциального обмена/продажи.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | string PK | Универсальный ID |
| `account_id` | string FK nullable, unique | NULL — зарезервированный UIN, ещё не выдан |
| `number` | string unique | Сама последовательность цифр |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

## UIN — генерация

- **Формат:** только цифры. Длина начинается с **4** (1000–9999).
- **Авторасширение:** когда пул длины N исчерпан — генератор переключается на N+1. Максимум 10 цифр.
- **Случайность:** UIN выдаются псевдослучайно, **не последовательно**. Сначала может прийти `4937`, потом `9378` — чтобы не давать оценку числа аккаунтов и не создавать "престиж" по счётчику.
- **Асинхронность:** регистрация **не блокируется** генерацией. Account создаётся, ставится task в очередь генерации UIN, фронт получает UIN позже (поллинг или push).
- **Коллизии:** unique-индекс на `uins.number` + retry в задаче. Очередь — BullMQ на Redis (см. [`backend-stack.md`](backend-stack.md)).

## "Красивые" UIN

`1111`, `2222`, `12345`, `11111`, повторы, лесенки и т.п. — резервируются заранее скриптом со `account_id = NULL`. На будущее — монетизация (продажа/обмен). Конкретный список паттернов и правила резервирования — отдельный TODO.

## Username

- **Длина:** 3–30 символов включительно.
- **Алфавит:** `a-z`, `A-Z`, `0-9`.
- **Регистронезависимый** — `Petya` и `petya` считаются одним именем (для поиска и уникальности).
- **Кому выдаётся:** только своим — вручную админом через БД или через админ-панель в приложении. Юзер сам username не выбирает.

Username — **не login**. Это "ник для своих", фича доверенных аккаунтов.

## Login

**Login = UIN.** Username опционален и есть не у всех.

- Пароль хешится **на сервере**, **argon2id**. Plain-text идёт по TLS (допустимо: реальный секрет — приватные ключи чатов — на сервер не попадает).
- Клиент поддерживает **мульти-аккаунт**: несколько Account залогинено одновременно, переключение в UI.
- Восстановление пароля — через секретные вопросы. Подробнее: [`recovery.md`](recovery.md).

## Регистрация — flow

1. Юзер вводит пароль и (если `feature-flags.free_registration === false`) инвайт-код. Запрос: `POST /api/v1/account/create` с `{ password, invite_code }`.
2. Бэк проверяет инвайт (если требуется), создаёт Account (без UIN), создаёт первую сессию, ставит задачу генерации UIN в очередь.
3. Бэк возвращает токены — фронт **сразу авторизуется**, не ждёт UIN.
4. На UI висит модалка/баннер: "Не выходите из аккаунта, пока не получите UIN — UIN это ваш логин, без него восстановить аккаунт нельзя."
5. Когда UIN сгенерирован — приходит WSS-событие `uin_assigned`, модалка снимается, UIN отображается в профиле. Альтернатива (если WSS не подключён): поллинг `GET /api/v1/uin/read-status`.

Это решение принято как **концептуальный workaround**, не как business-ready UX. Минусы (юзер всё-таки может выйти и потерять Account) осознаются — будут адресоваться позже.

## Поиск и взаимодействие

- **Поиск:** глобально по `username` и по `number` (UIN).
- **Открытие профиля:** доступно из результатов поиска.
- **Возможность писать:** зависит от настроек приватности целевого аккаунта (публичный / только инвайт / закрытый и т.п.). Конкретные настройки — отдельный TODO (не "потом-потом").
